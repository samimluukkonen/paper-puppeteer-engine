# Create a pull request

Arguments: $ARGUMENTS

## Current state

Branch:

!`git branch --show-current`

Working tree:

!`git status --short`

Recent commits:

!`git log --oneline -10`

## Arguments

- A bare word is the base branch. Without one, use the repository's default branch, `master`.
- `--draft` opens the pull request as a draft.
- `--dry-run` shows the title and description and stops, without pushing or creating anything.

## Procedure

Use `gh api` (GitHub's REST API) for every GitHub call, not `gh pr` or other GraphQL-based commands. `gh api` works both locally and in Claude Code cloud sessions, and it fills in `{owner}` and `{repo}` from the git remote.

### 1. Check the branch

- If the current branch is the base branch, stop. Ask the user which branch to create for the work instead of opening a pull request from the base.
- If the working tree has uncommitted changes, stop and ask whether to commit them first or leave them out. A commit uses a plain `git commit -m` message, with no Co-Authored-By, "Generated by" or other tool attribution (AGENTS.md).
- Run `git fetch origin <base>`. Then list the branch's own commits with `git log --format='%h %s' origin/<base>..HEAD`. If there are none, stop and say there is nothing to propose.

### 2. Look for an existing pull request

Run:

```bash
gh api 'repos/{owner}/{repo}/pulls?head={owner}:<branch>&state=open' --jq '.[] | "\(.number) \(.html_url)"'
```

If one is open, give the user its link and stop. Offer to update its description with `gh api -X PATCH 'repos/{owner}/{repo}/pulls/<number>' -F body=@<file>` instead of opening a second one.

### 3. Make sure the checks are known

Use check results from this conversation if they cover the current `HEAD`. Otherwise, start the `verifier` subagent in the foreground (`run_in_background: false`) with its default ladder and wait for it. Run no other test, build or profile command while it works.

If a check fails, stop and report it instead of opening the pull request, unless the user asked for a draft. In that case, open the draft and list the failure in the description.

### 4. Write the title and description

Read what the branch changes before writing:

- `git diff --stat origin/<base>...HEAD`
- `git diff origin/<base>...HEAD -- CHANGELOG.md package.json`
- the plan files under `plans/` that the branch adds or changes, if any.

**Title:** one plain sentence in the style of this repository's commit subjects, for example "Escape rig inspector number-field attributes and record the reverted per-frame allocation trial". With one commit, use its subject.

**Description:** the repository has no pull request template. Use these sections, in this order:

```markdown
## Summary

<One to three sentences: what changes and why.>

## Changes

- <Grouped bullets for the main changes, naming the files or modules a reviewer should look at first.>

## Changelog

<The bullets this branch adds to CHANGELOG.md, and the heading they are under. If the version changes, say from and to. Write "None" if there are no changelog entries.>

## Verification

- <Each command that ran and its result, for example `npm test`: 276 files and 4604 tests passed.>
- <Local browser checks, only if they actually ran, marked as local.>

## Notes

<The plan the branch implements, recorded decisions, known limitations and follow-ups. Leave the section out if there are none.>
```

Write only what the branch and the conversation show. Do not list checks that did not run. Do not suggest adding browser tests to CI.

If the arguments include `--dry-run`, show the title and description and stop here.

### 5. Push the branch

Run `git push -u origin <branch>`. Retry network errors up to four times, waiting 2, 4, 8 and 16 seconds.

If the push is rejected because the remote branch has commits that are missing locally, never force-push. Run `git fetch origin <branch>` and `git merge --no-edit FETCH_HEAD`, push again, and tell the user.

### 6. Create the pull request

Write the description to a temporary file outside the repository, then run:

```bash
gh api -X POST 'repos/{owner}/{repo}/pulls' \
  -f title='<title>' \
  -f head='<branch>' \
  -f base='<base>' \
  -F draft=<true|false> \
  -F body=@<description file> \
  --jq '"\(.number) \(.html_url)"'
```

Delete the temporary file afterwards.

### 7. Report

Give the pull request's link, number, base branch and whether it is a draft. Say that the "Check and deploy to GitHub Pages" workflow runs its checks job on pull requests: audit, format, lint, typecheck, unit tests, build, demo pages and the packed package. Deployment happens only from `master`.
