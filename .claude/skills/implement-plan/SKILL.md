# Implement a plan

Plan to implement: $ARGUMENTS

## Current state

Package version:

!`node -p "require('./package.json').version"`

Latest changelog headings (line numbers in `CHANGELOG.md`):

!`grep -n -m 15 '^## ' CHANGELOG.md`

Working tree:

!`git status --short`

## Procedure

AGENTS.md rules always apply. This procedure adds the order of work and the details AGENTS.md leaves implicit.

### 0. State the targets before editing

Before changing any file, tell the user:

- the plan type: a version plan (`plans/plan-v…` or `plans/archive/plan-v…`) or an architecture/other plan;
- the changelog heading the entries will go under;
- whether `package.json` will change, with the current and target versions.

If the user asked only for these targets, stop here.

### 1. Read the plan

Read the whole plan file, including any "Recorded decisions", "Out of scope", "Definition of done" and "Final report" sections. If the plan changes any view, header, inspector, panel or stylesheet, also read `docs/style-guide.md`. Check the plan's `path:line` references against the current code; they may predate later commits.

### 2. Map the plan version to SemVer

Version plans take their milestone from the filename (`plan-v1.6.2.2.md` is milestone `1.6.2.2`). The first three numbers are the release. Any further numbers are joined with `.` and become the prerelease after `-`. This is the convention on line 3 of `CHANGELOG.md`.

| Milestone   | Changelog heading and package version |
| ----------- | ------------------------------------- |
| `1.6.6`     | `1.6.6`                               |
| `1.6.2.2`   | `1.6.2-2`                             |
| `0.9.8.2`   | `0.9.8-2`                             |
| `0.5.2.8.3` | `0.5.2-8.3`                           |

Architecture plans and plans without a version put their entries under `## Unreleased`, unless the plan names another heading.

### 3. Write the changelog entries

- Use plain `-` bullets in the style of the neighbouring entries. Do not add Fixed/Added/Security subheadings.
- Put version-plan entries under that version's `## <semver>` heading, never under Unreleased.
- If the heading does not exist, create it at its descending SemVer position: below `## Unreleased`, above every lower version. A prerelease sorts below its release, so `1.6.2` comes before `1.6.2-2`, and `1.6.2-2` before `1.6.2-1`. Older milestones go at their correct position further down, not at the top.

### 4. Update the package version only upward

Compare the plan's SemVer with the current package version above.

- If the plan's version is higher, run `npm version <semver> --no-git-tag-version`. It updates `package.json` and both version fields in `package-lock.json`, and creates no commit or tag.
- If it is equal or lower, leave `package.json` and `package-lock.json` unchanged. Never downgrade.

Then run `npm run check:version`. `scripts/check-version.mjs` requires the package and lockfile versions to agree and `CHANGELOG.md` to have a `## <package version>` heading.

### 5. Implement

Work through the plan in its order. Where the plan says items can land as separate commits, keep them separate. Commit only when the user asks, using a plain `git commit -m` message with no Co-Authored-By, "Generated by" or other trailer.

For a measure-then-keep item (the architecture-17 and architecture-19 pattern):

1. Run the plan's profile command twice at the starting commit, with one worker, and note the medians.
2. Make the change and run the profile twice again.
3. Keep the change only if both runs show a clear improvement beyond run-to-run noise, with the full suite green. Otherwise revert it.
4. Either way, record a before/after table in the plan under "Recorded decisions".

Profiles have no thresholds; do not add any. Never run a profile at the same time as tests or browser checks.

### 6. Verify

- Hand the plan's Verification commands to the `verifier` subagent, started in the foreground (`run_in_background: false`). Run no other test, build or profile command while it works.
- If the change touches UI, also run the `ui-style-reviewer` subagent on the diff and fix the findings that apply.
- Run browser smoke tests (`npm run test:browser`) only locally and only when the plan or the user asks. Never add them to CI.
- Run `npm run format` after editing Markdown, TypeScript or CSS outside `plans/`.

### 7. Record decisions in the plan

For architecture plans, add outcomes under `## Recorded decisions`: what was kept or reverted, why, the date, and the commit it was measured at. `plans/` is excluded from oxfmt, so keep the existing hand formatting.

### 8. Report

If the plan has a `## Final report` section, answer each of its numbered items in your reply, including exact command results. Otherwise summarise what changed, the files touched and the check results. Do not claim completion while a required check fails; say which check failed and why.
