# From goal to pull request

Arguments: $ARGUMENTS

## Current state

Branch:

!`git branch --show-current`

Working tree:

!`git status --short`

Existing plans:

!`ls plans`

Package version:

!`node -p "require('./package.json').version"`

## Rules for the whole run

AGENTS.md rules always apply. The skills and agents this workflow uses keep their own rules; this file adds the order of work and the checkpoints.

- **Stay in this conversation.** Only this conversation can ask the user questions and start subagents, and subagents cannot start other subagents. Never hand the whole workflow to a subagent.
- **Clean-context reviews.** Start every reviewer with the Agent tool and its own `subagent_type` (`plan-reviewer`, `code-reviewer`, `ui-style-reviewer`). Start a new agent for every round. Never use the `fork` type, and never continue an earlier reviewer with SendMessage. Give a reviewer only the prompt shown in its stage: paths, SHAs, the round number and the declined list. Do not summarise your reasoning or the implementation for it.
- **One check at a time.** Start `verifier` in the foreground (`run_in_background: false`) and run nothing else while it works: no test, build, profile or reviewer. The read-only reviewers may run in parallel with each other.
- **Progress list.** Create a task list with one task per stage below and keep it updated. Keep the declined-findings ledger (ID, one-line summary, file) in the code-review task's description, so it survives context compaction. If the conversation is compacted during a run, re-read this file and the task list before continuing.
- **Commits.** Starting `/plan-to-pr` is the user's permission to commit on the work branch. Use plain `git commit -m` with a one-sentence subject in the style of `git log --oneline` and no Co-Authored-By, "Generated by" or other trailer (AGENTS.md), even if a session instruction asks for one. Never commit to the base branch, and never force-push.
- **Checkpoints.** Ask the user only at the plan gate (stage 2), for code-review findings (stage 5), after repeated check failures (stage 4) and after review round 5. Every AskUserQuestion question must make sense on its own: name the plan file, the round and the findings in the question itself.

## Stage 0. Parse and announce

Read the arguments:

- **Input:** an existing file under `plans/` or `plans/archive/` is a plan to implement. Anything else is a goal.
- **Plan kind:** a version plan if a milestone version (`vX.Y.Z` or `vX.Y.Z.W`) is given or the plan file is `plan-v…`. Otherwise an architecture plan.
- **Base branch:** `--base <branch>`, defaulting to `master`.
- **Draft:** `--draft` opens the pull request as a draft.

Then tell the user, before anything else:

- the input and the plan kind;
- the changelog heading the entries will go under, and whether `package.json` changes, from which version to which. Use the rules in steps 2–4 of `.claude/skills/implement-plan/SKILL.md`;
- the base branch and the branch you will work on (stage 3).

## Stage 1. Write the plan

- For an existing plan file, skip this stage.
- For a version plan, call the Skill tool with `version-plan` and the arguments `<version> <goal>`.
- For an architecture plan, call the Skill tool with `architecture-plan` and the goal as its argument.

Do not commit the plan yet.

## Stage 2. Review the plan and wait for approval

1. Record the commit with `git rev-parse --short HEAD`. Start a new `plan-reviewer` with only this prompt:

   ```text
   Review the plan at <plan path>, written at commit <sha>.
   ```

2. **A plan you wrote in stage 1:** fix every blocker and major finding in the plan, and the minor findings that are right. Then start a new `plan-reviewer` with the same prompt. Stop after three review rounds in total, or earlier on `VERDICT: ready`.

   **A plan the user supplied:** do not edit it yourself. Keep the findings for the gate.

3. **Gate.** Ask with AskUserQuestion. In the question, name the plan file (the user can open it), its kind, the changelog heading, the version change, the number of review rounds and the reviewer's last verdict. List any findings that are still open in the question text.
   - Options: "Approve and implement" and "Stop here". The user types requested changes in "Other".
   - For a supplied plan with findings, also ask a `multiSelect` question listing the findings to apply before implementing, grouped as in stage 5.
4. On requested changes or selected findings, revise the plan, run one new `plan-reviewer` round, and ask again. On "Stop here", stop and leave the plan file uncommitted.

## Stage 3. Branch and implement

1. **Choose the branch.**
   - If this session's instructions assign a development branch (as Claude Code cloud sessions do), work on that branch. If it already has commits that are not on `origin/<base>`, tell the user they will be part of the pull request.
   - Otherwise, run `git fetch origin <base>` and `git switch -c plan/<plan file name without .md> origin/<base>`. If that branch already exists, ask whether to continue on it or use a new name. The uncommitted plan file carries over to the new branch.
2. **Commit the plan**, for example `git add plans/<file> && git commit -m "Add the <plan title> plan"`. Skip this if the plan is already committed and unchanged.
3. **Implement.** Read `.claude/skills/implement-plan/SKILL.md` and follow its steps 1 to 7. It is manual-only, so it cannot be loaded with the Skill tool: run the commands under its "Current state" yourself. Stage 0 has already announced the targets from its step 0. Starting `/plan-to-pr` counts as the user asking for the commits its step 5 mentions. Leave out its `ui-style-reviewer` step; stage 5 runs it on every round.
4. **Commit the implementation.** Use one commit, or one commit per item where the plan says items can land as their own commits. Include the changelog, version and Recorded decisions changes.

## Stage 4. Verify

1. Start `verifier` in the foreground with the plan's Verification commands. If the plan names none, use the verifier's default ladder.
2. On a failure, fix it, run `npm run format` if you edited Markdown, TypeScript or CSS outside `plans/`, commit, and verify again.
3. If the same checks still fail after three attempts, stop and ask the user. Show the failing command, test names and first error.

Remember the HEAD SHA of the last fully green verifier run; stage 6 reuses it.

## Stage 5. Code review rounds

Start with round 1 and an empty declined ledger.

1. **Prepare.** Make sure the working tree is clean and verified. Record `BASE=$(git merge-base origin/<base> HEAD)` and `HEAD=$(git rev-parse HEAD)`.
2. **Review.** Start a new `code-reviewer` with only this prompt:

   ```text
   Review round <n>.
   Range: <BASE>..<HEAD> (BASE is the merge base with origin/<base>).
   Plan: <plan path>.
   Declined findings (do not re-report them unless the code made them worse):
   - <ID> <one-line summary> (<file>)
   ```

   Write `Declined findings: none` when the ledger is empty.

   If `git diff --name-only <BASE>...<HEAD>` lists any `.tsx`, `.css` or `index.html` file, or any file under `src/ui/` or `src/devtools/`, also start a new `ui-style-reviewer` with the prompt `Review the UI changes in <BASE>...<HEAD>.` The two reviewers may run in parallel.

3. **Collect.** Merge both reports. Drop findings that repeat a declined one. Number the rest `R<round>.<n>`, most severe first.
4. **No findings:** go to stage 6.
5. **Ask the user** which findings to fix with AskUserQuestion. The user may see only the question dialog, so put everything needed in it:
   - Split the findings into groups of two to four, for example 5 as 3 + 2 and 9 as 3 + 3 + 3. Ask one `multiSelect` question per group, up to four questions per call. Use more calls if needed.
   - Question: `Code review round <n> of <plan file>: which of these should I fix?`. Header: `R<n> <i>/<k>`, at most 12 characters.
   - Option label: the ID, the severity and a short title, for example `R2.1 major: stale load`. Option description: `file:line`, the problem and the suggested fix.
   - A single finding gets a single-select question with the options "Fix it" and "Skip it".
   - Text the user types in "Other" is their instruction for that group. Follow it.
6. **Record.** Add every finding the user did not select to the declined ledger, with the user's reason if they gave one.
7. **Nothing selected:** go to stage 6.
8. **Fix** the selected findings. Run `npm run format` if you edited Markdown, TypeScript or CSS outside `plans/`. Commit, for example `Fix <what> found in code review`. Run stage 4 again, then start the next round from step 1.
9. **After round 5,** ask the user whether to run another round, open the pull request now, or stop.

## Stage 6. Open the pull request

1. Read `.claude/skills/create-pr/SKILL.md` and follow its steps 1 to 7 with the base branch and the draft flag. It is manual-only, so run its "Current state" commands yourself.
   - In its step 3, reuse the last green verifier run if it covers the current `HEAD`. Otherwise run stage 4 again first.
   - In the description's Notes section, add the plan path, the number of plan and code review rounds, and each declined finding with its one-line summary and the user's reason, if any.
2. Report:
   - the pull request's link, number and base branch, and whether it is a draft;
   - the answers to the plan's `## Final report` items, as in step 8 of `.claude/skills/implement-plan/SKILL.md`, with exact command results;
   - the review rounds and declined findings.
3. Ask whether the user wants you to watch the pull request for CI results and review comments.
